## 2. The Numbers Explained

The MÚSpel Engine uses the native .NET four-field version scheme. Each field has a defined owner and purpose. They are not interchangeable, and they are certainly not decorative — every field carries a specific meaning that the engine can stand behind.

```
Major.Minor.Build.Revision
```
**Example:** `1.2.2605.2609`  
Reads as: **Major** = main version, **Minor** = module/feature addition, `2605` = **Build** date (auto-generated), `2609` = **Revision** date (auto-generated).

The table below defines each field precisely. The subsections that follow explain the intent behind each one.

| Field | Owner | Purpose | Format |
|:---|:---|:---|:---|
| **Major** | Developer | Overall base-logic change or breakage | `1` → `2` |
| **Minor** | Developer | Module/Feature addition (non-breaking) | `2` → `3` |
| **Build** | Dagr | YYMM build date (auto-generated) | `2605` (May 2026) |
| **Revision** | Dagr | YYMM last hotfix date (auto-generated) | `2609` (September 2026) |

### 2.1 Major — Overall Base-Logic Change or Breakage

A **Major** version increment signals a fundamental change to the engine's overall base logic — a rebuilt foundation, a replaced mechanism, a refactor of key parts, or a change that breaks compatibility with what came before. The principle of what the engine does may remain the same, but the execution underneath is fundamentally different.

A practical example: the engine currently uses AES-256-GCM with GCM authentication tags throughout. If that were to be replaced with a different cryptographic mechanism (e.g. HMAC), the principle, workflow and end result remain the same — data is encrypted, integrity is verified — but the processing method and output format are incompatible. Data encrypted under the old mechanism cannot be served by the new one. That is a **Major** increment.

At the module level specifically, a rewrite that fundamentally changes how that module processes or operates is equally a Major increment — even if nothing is visibly removed from the surface. The internal change is a breaking change.

**Major is the loudest signal in the versioning contract.** Every connected application must be verified compatible before it runs. If it cannot be verified — it is refused.

### 2.2 Minor — Module/Feature Addition (non-breaking)

A **Minor** version increment signals a non-breaking addition to the engine — a new module, a new capability, or a clean internal refactor that produces no change in external behaviour. Same input, same output, same interface. Nothing that worked before is broken or changed.

The distinction from **Major** is precise: if the addition or change is invisible to everything outside the module — it is Minor. The moment it affects processing, output format, or compatibility — it becomes **Major**.

**Minor adds. It never breaks.**

### 2.3 Build Date — Auto-generated by Dagr

The **Build** field records the date the build was compiled, in `YYMM` format. It is auto-generated by Dagr at build time — NTP when the build machine is connected, RTC when air-gapped. No manual input is permitted.

This is unverified WORKING time — never ATTESTATION time. NTS would be over-engineering and prevent compiling from air-gapped workstations.

When **Build** and **Revision** are equal, the build is clean and unpatched.

### 2.4 Revision — Also Auto-generated by Dagr

The **Revision** field records the date of the last hotfix applied to a build, in `YYMM` format. Like the **Build** date, the **Revision** is also auto-generated by Dagr, at the moment of applying the hotfix.

A hotfix is a small, targeted correction or repair-focused update — a misplaced operator, a minor fix — that does not warrant a **Major** or **Minor** increment. Only the **Revision** date moves. **Major**, **Minor**, and **Build** remain frozen.

This is unverified WORKING time — never ATTESTATION time, for the same reasons as the **Build** field.

When **Build** ≠ **Revision**, the build has been patched since it was compiled. The gap between the two dates is the patch history, readable at a glance. No separate patch registry needed — the version number carries its own record. The dates can be tracked by their corresponding CHLG documentation.

### 2.5 The 16-Bit Discipline

Each field in the .NET version scheme is a 16-bit unsigned integer — capable of holding values from 0 to 65535. A four-digit `YYMM` date fits comfortably within that ceiling.

This constraint is embraced as discipline, not worked around. It keeps version numbers human-readable and meaningful at a glance — rather than degenerating into opaque build hashes that serve tooling but communicate nothing to a reader. Every field carries a specific, readable value. That is by design.

## 3. Field Ownership & Purpose

The four fields divide into two distinct pairs, each with a different owner and a different purpose.

| Pair | Fields | Owner | Purpose |
|:---|:---|:---|:---|
| **Meaning** | **Major** + **Minor** | Developer | What kind of change is this? Earned by a real change — never claimed. |
| **Time** | **Build** + **Revision** | Dagr | When was it compiled and last patched? Auto-generated facts — never manual. |

The compatibility gate reads only the **Meaning** pair — **Major** and **Minor**. The **Time** pair carries the dates and is never consulted for compatibility. A rebuild with a new date but identical **Major**.**Minor** is compatibility-identical. The date moving alone never signals a change to a connected application.

---

## 4. Version Number as Self-Contained Record

On the day a **Major** or **Minor** build is compiled, **Build** and **Revision** are equal — no hotfix has been applied yet. A clean, unpatched build always has matching date fields.

The gap between **Build** and **Revision** is the patch history — readable at a glance, without the need for a separate patch registry or database. The corresponding CHLG documentation records what was changed and complements the **Revision** number.

> For more details, see sub-section 2.4.

**Worked example:**

| Event | Version | State |
|:---|:---|:---|
| Initial release, May 2026 | `1.0.2605.2605` | **Major** version 1, no hotfixes applied |
| Module added, September 2026 | `1.1.2609.2609` | **Minor** increment, no hotfixes applied |
| Hotfix applied, October 2026 | `1.1.2609.2610` | **Build** unchanged, hotfix date updated |

## 5. Maturity States

Every build carries two identifiers: a version number and a maturity tag. They are separate by design — the four-field version number is numeric only and cannot hold a text tag. The maturity tag lives in a dedicated .NET companion field, called the `InformationalVersion` string.

It is Vǫr who reads the maturity tag at connect time. A version number below 1.0 does not bar a build from being taken into production, the tag does. The tag is governed by the rules and guidelines stated in the Internal Development Status Index.

> For more details, see ED-INDX-IDSI-000.

### 5.1 Born To `-dev`

The `-dev` tag marks a build as being in **Development** — whether actively in progress or parked as inactive. It is the exclusive tool of the Developer License holder — intended for their own development environment only.

A `-dev` build is loadable only under a Developer License or Creator License. In any other context, it is refused — hard refusal, not a warning. It may or may not boot cleanly — no floor requirement applies. It cannot be shipped to clients or tested by any external party under any circumstance.

The `-dev` tag is also the honest residue on any build abandoned mid-development. A build that never cleared the floor never earns the right to drop the tag. A build that never cleared the floor stays tagged — by definition, not a release.

### 5.2 The `-RC` To Be

The `-RC` tag marks a build that is production-loadable and under real-world testing. It is the missing rung between **Development** and **Stable** — proven in a controlled environment, but not yet proven in the wild.

An `-RC` build must boot cleanly — the launch floor is non-negotiable. Its changelog may still be in progress, with features being completed under real production conditions. This is intentional. The `-RC` exists to allow a developer to exercise already-implemented functions against real users before the final, complete-changelog release — rather than shipping blind.

An `-RC` build is production-loadable. It is not yet a promise.

### 5.3 From Able to `-Stable`

The `-Stable` tag marks the end of active development and testing. This is the moment where it stops being an idea or test-case, and turns into a commercial stable product. It is the only tag that carries the full weight of the versioning contract.

A `-Stable` build must boot cleanly. It must fully honour its changelog — everything claimed as present and working, is present and working. Minor bugs are allowed. Broken changelog claims are not.

The distinction between `-RC` and `-Stable` is human-facing and contractual — it lives in the Developer License terms, not in a machine check. The engine cannot read a changelog. The developer is bound by it per agreement.

### 5.4 The Maturity Ladder

The three tags form a clear progression — from active development to cautious deployment to full release. Each step carries a higher threshold and a stronger commitment.

Any developer must adhere to this development scheme. Compliance is one of the conditions of the Developer License.

| Tag | Status | Deployable | Threshold |
|:---|:---|:---|:---|
| `-dev` | Development / Inactive | No — hard refused | None |
| `-RC` | Release Candidate | Yes | Boot clean, changelog in progress, bugs allowed |
| `-Stable` | Stable Release | Yes | Boot clean, changelog honoured, no major bugs |

### 5.5 Your Product. Our Quality Seal.

A developer is free to implement any distribution channel their application requires — staged rollouts, opt-in beta access, hidden preview tracks, or any other delivery mechanism. That is entirely their business.

The maturity tag, however, is an engine-level contract. A `-dev` build remains refused outside a Developer or Creator License context, regardless of how it was packaged, shipped or delivered. The tag travels within the build. The engine reads and validates the tag. No exceptions.

## 7. Earned, Not Claimed

A version number is a factual record, not a marketing tool. Every increment must correspond to a real, verifiable change. Vanity bumps — inflating a number to appear more mature, more capable, or further along than the software actually is — are not just dishonest, they are a liability. A developer who ships a misleading version number is not only misrepresenting their product to Era Digital — they are misrepresenting it to their own clients.

**Major** and **Minor** are the Developer's responsibility. They are earned by real change and declared with intent. **Build** and **Revision** are beyond anyone's reach — Dagr generates these from real time at the moment of compilation or hotfix. No developer can backdate a build or forward-date a patch. The time fields are a matter of record, not preference.

The Era Digital ecosystem is built on substance and trust — between the engine, the developer, and the end user. A version number that cannot be trusted, breaks that chain. The standard exists to keep these core values intact.

## 8. To Each Their Own

Versioning and licensing are orthogonal by design. They operate independently and have no knowledge of each other.

A license answers two questions only: currency and accessibility. A version number answers one question only: the compatibility level of the software. Neither can substitute for the other, and neither overrules the other.

A valid license entitles the holder to the current version — whatever it is. A **Major** version bump does not invalidate a license. A foundation rebuild does not cost extra. Whatever ships while the license is valid, is included.

This independence is also a structural safeguard for the *Earned, Not Claimed\** principle. The business model and the versioning model are aligned by design. Revenue is time-based and quality-driven, not version-based — removing any incentive to manufacture progress that does not exist.

## 9. The App-titude Test

Vǫr is the version and compatibility authority. When an application connects through Bifrǫst, Vǫr validates both the engine version and the application's declared requirement before anything else takes place. A malformed version on either side is rejected immediately, before any comparison is attempted.

Where both versions are valid, Vǫr compares **Major** first. The engine **Major** must be equal to or greater than the application's declared requirement — if not, the application is refused. It may rely on breaking changes the engine does not carry. **Minor** is compared next, on the same principle. If the engine **Minor** falls below what the application requires, it is refused — it may call capabilities that do not yet exist.

Finally, the maturity tag is applied. A `-dev` build is admissible only under a Creator or Developer License ExecutionContext. In any other context, it is refused without exception.

Vǫr returns one of three outcomes: Admitted, Refused, or Error — each accompanied by a plain reason string.

Vǫr never touches license governance. That is Týr's domain — Vǫr, or any other module for that matter, never crosses that line.
